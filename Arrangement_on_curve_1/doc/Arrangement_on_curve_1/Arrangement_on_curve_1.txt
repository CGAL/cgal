\section aoc_sec-intro Introduction
<!-- ======================================================================= -->

The package `Arrangement_on_curve_1` is designed for constructing,
manipulating, and querying one-dimensional arrangements embedded along
continuous curves referred to as *master curves*. A 1D arrangement
offers an efficient mechanism to maintain ordered sequences of points
across diverse geometric tracking scenarios.
\cgalFigureRef{aoc_fig-semicircle} shows a 1D arrangement embedded on
the closed upper semicircle.  It has seven vertices
\f$v_0,v_1,...,v_6\f$ and six edges \f$e_0, e_1, ..., e_5\f$; see
\ref Arrangement_on_curve_1/arr_on_circle_segment.cpp.

\cgalFigureBegin{aoc_fig-semicircle,semicircle.png}
\cgalFigureEnd

<!-- ----------------------------------------------------------------------- -->
\subsection aoc_ssec-intro-sep Separation of Topology and Geometry
<!-- ----------------------------------------------------------------------- -->

Following standard \cgal architectural practices, this package
strictly isolates the topological framework from the underlying geometry.
- **Topology** describes the incidence relations (left or right)
  between vertices and edges and the topology of the master curve.
- **Geometry** encapsulates geometric predicates and geometric object
  constructions required to compute relative ordering along a master curve.

The core arrangement structure handles its geometry traits via a
shared smart pointer (`std::shared_ptr<const Geometry_traits_1>`) to
optimize lifecycle safety and reference tracking during intensive
geometric operations. This allows sub-arrangements or output results
to safely share identical geometric contexts with zero duplication
overhead.

<!-- ----------------------------------------------------------------------- -->
\subsection aoc_ssec-intro-boundary Parameter Space and Boundary Categories
<!-- ----------------------------------------------------------------------- -->

The master curve \f$C = \phi_C(X)\f$ is given by a continuous function
\f$\phi_C: X \rightarrow \mathbb{R}^d\f$; it is defined over a
one-dimensional interval \f$X\f$ called the parameter space. The
parameter space can be open, half-open, closed, or identified. Each
geometry traits model declares two category types that determine the
boundary conditions of both sides of the parameter space,
respectively:

- `Left_side_category`: the boundary condition of the left side of the curve's parameter space.
- `Right_side_category`: the boundary condition of the right side of the curve's parameter space.

Each category type above is defined as one of the three tag types below:

| Tag                   | Meaning                                             |
|-----------------------|-----------------------------------------------------|
| `Open_side_tag`       | The boundary side is open                           |
| `Closed_side_tag`     | The boundary side is closed                         |
| `Identified_side_tag` | The boundary side is identified with the other side |

The combination of the two category tags determines which topology
traits class to pair with the geometry traits; see \ref aoc_sec-topo_traits.

<!-- ----------------------------------------------------------------------- -->
\subsection aoc_ssec-intro-outline Outline
<!-- ----------------------------------------------------------------------- -->

This manual walks through the structural elements of basic 1D
subdivisions, methods for traversing topology pools, techniques for
point location, procedures for overlay operations, the requirements
for writing custom geometry traits, the topology traits classes and
their shared infrastructure, the mechanism for extending arrangement
cells (i.e., vertices and edges), and the means of accessing cell
properties (including extended data) via property maps.

The types and free functions referred to throughout this chapter are
defined under the namespace `CGAL::Arrangement_on_curve_1`.

<!-- ======================================================================= -->
\section aoc_sec-basic Basic Arrangements
<!-- ======================================================================= -->

<!-- ----------------------------------------------------------------------- -->
\subsection aoc_ssec-basic-rep Representation of Arrangements
<!-- ----------------------------------------------------------------------- -->

A 1D arrangement subdivides a continuous curve into two alternating
topological cells:
- **Vertices**: Represent 0-dimensional points embedded along the curve master.
- **Edges**: Represent 1-dimensional open intervals bounded by vertices on their left, right, or open.

<!-- ----------------------------------------------------------------------- -->
\subsection aoc_ssec-basic-arr_class The Arrangement Class Template
<!-- ----------------------------------------------------------------------- -->

The primary interface is provided by the class template
`Arrangement_on_curve_1<GeometryTraits_1, TopologyTraits, BinarySearch>`,
which models the concept `ArrangementOnCurve_1`.
It exposes safe APIs for query evaluations while delegating memory
container allocations, incidence cell updates, and property map
indexing to the backend topology traits model.

When `TopologyTraits` is omitted it defaults to
`Open_topology_traits<GeometryTraits_1>`, which is correct for any
geometry traits with `Left_side_category = Right_side_category =
Open_side_tag`.  For other combinations supply the matching traits
explicitly, e.g.:

\code{.cpp}
using K = CGAL::Exact_predicates_exact_constructions_kernel;
using Gt = CGAL::Arrangement_on_curve_1::Circle_traits_1<K>;
using Tt = CGAL::Arrangement_on_curve_1::Identified_topology_traits<Gt>;
using Arr = CGAL::Arrangement_on_curve_1::Arrangement_on_curve_1<Gt, Tt>;
\endcode

An empty arrangement consists of a single edge representing the whole master curve.

<!-- ----------------------------------------------------------------------- -->
\subsection aoc_ssec-basic-traverse Traversing the Arrangement
<!-- ----------------------------------------------------------------------- -->

Neighbor-to-neighbor structural traversals can be performed in either
direction along the chain using incidence descriptor accessors
like `ArrangementOnCurve_1::left_edge()`,
`ArrangementOnCurve_1::right_edge()`,
`ArrangementOnCurve_1::left_vertex()`, and
`ArrangementOnCurve_1::right_vertex()`.

The arrangement vertices and edges can be traversed using descriptor iterators.
Callers can query all vertices or edges globally via ranges:
\code{.cpp}
for (auto v_desc : arr.vertices()) {
  // Access information using property maps...
}
\endcode

<!-- ----------------------------------------------------------------------- -->
\subsection aoc_ssec-basic-modify Modifying the Arrangement
<!-- ----------------------------------------------------------------------- -->

Arrangements can be dynamically built or modified using primitive
update methods.  When an arrangement is entirely empty, it consists of
a single edge representing the whole master curve.  Inserting the very
first point `p` into an arrangement object `arr` uses \link
ArrangementOnCurve_1::insert_empty() `arr.insert_empty(p)`\endlink.
For open curves this splits the single edge into a left edge and a
right edge flanking the new vertex.  For identified curves it creates
the first vertex and a single loop edge with both endpoints at that
vertex.

<!-- ----------------------------------------------------------------------- -->
\subsection aoc_ssec-basic-insert Inserting Points
<!-- ----------------------------------------------------------------------- -->

The arrangement class provides low-level topological construction
modifiers to handle structured manual assembly:

- The call \link ArrangementOnCurve_1::insert_before() `arr.insert_before(v, p)`\endlink
  inserts a new point `p` strictly to the left of an existing vertex `v`.

- The call \link ArrangementOnCurve_1::insert_after() `arr.insert_after(v, p)`\endlink
  inserts a new point `p` strictly to the right of an existing vertex `v`.

- The call \link ArrangementOnCurve_1::split_edge() `arr.split_edge(e, p)`\endlink
  subdivides an edge at the designated point `p`, introducing a new interior vertex.

Note that when the template parameter `BinarySearch` of
`Arrangement_on_curve_1<GeometryTraits_1, TopologyTraits, BinarySearch>`
is set to `true` (and `TopologyTraits::UseVector = true`):
- The function `ArrangementOnCurve_1::insert_before()` is not supported.
- The function `ArrangementOnCurve_1::insert_after()` can be used only if
  the new point extends the topology further toward \f$+\infty\f$.
- The function `ArrangementOnCurve_1::split_edge()` can be used only if
  the edge to split is the right boundary edge (spans to \f$+\infty\f$).

<!-- ----------------------------------------------------------------------- -->
\subsection aoc_ssec-basic-remove Removing Vertices and Edges
<!-- ----------------------------------------------------------------------- -->

A vertex `v` can be removed from the arrangement using the call
\link ArrangementOnCurve_1::remove() `arr.remove(v)`\endlink.

Removing a vertex removes its point from the track and merges its left
and right flanking edges back into a single unified edge, preserving
the overall topological continuity of the curve.

<!-- ======================================================================= -->
\section aoc_sec-free_funcs Free Functions
<!-- ======================================================================= -->

<!-- ----------------------------------------------------------------------- -->
\subsection aoc_ssec-free_locate Issuing Queries
<!-- ----------------------------------------------------------------------- -->

Given a query point \f$q\f$, the call \link locate() `locate(arr, q)`\endlink
locates the query point `q` in the given arrangement `arr`. The function returns
a discriminated union container of type `ArrangementOnCurve_1::Const_location_result`
(an instance of `std::variant`) that identifies a cell (i.e., a vertex or an edge).
In particular, the result is a `Vertex_const_descriptor` if the geometric
embedding of the identified vertex coincides exactly with the query point \f$q\f$,
or otherwise an `Edge_const_descriptor`, such that the geometric embedding of the
identified edge contains \f$q\f$ in its interior.

The search is a linear topological walk from left to right starting at
\link ArrangementOnCurve_1::left_boundary_edge()
`left_boundary_edge()`\endlink.  When `BinarySearch = true` and
`TopologyTraits::UseVector = true`, the search uses binary search over
the sorted vertex vector, reducing point location from \f$O(n)\f$ to
\f$O(\log n)\f$.

A similar function that returns an object of type
`ArrangementOnCurve_1::Location_result` storing a non-const descriptor
is also supported.

<!-- ----------------------------------------------------------------------- -->
\subsection aoc_ssec-free_insert Inserting Points
<!-- ----------------------------------------------------------------------- -->

A high-level free function to insert points into the arrangement is provided.
The call \link insert() `insert(arr, p)`\endlink
invokes the function. It first calls
\link locate() `locate(arr, p)`\endlink
internally to find where the point `p` is located. If the point
already matches an existing vertex, the descriptor of that vertex is
returned. Otherwise, the function invokes
`ArrangementOnCurve_1::insert_empty()`,
`ArrangementOnCurve_1::insert_before()`,
`ArrangementOnCurve_1::insert_after()`, or
`ArrangementOnCurve_1::split_edge()`
as needed to safely update the topology.

<!-- ----------------------------------------------------------------------- -->
\subsection aoc_ssec-free_overlay Overlaying Two Arrangements
<!-- ----------------------------------------------------------------------- -->

The call \link overlay() `overlay(arr_a, arr_b, arr_r)`\endlink
combines two input arrangements `arr_a` and `arr_b` aligned along the
same continuous supporting curve into a single unified output
arrangement `arr_r` (embedded in the same underlying curve).  The
algorithm performs a synchronized left-to-right sweep across both
structures simultaneously.

An overloaded version accepts a fourth argument, referred to as the
visitor, is also supported. As intersections, point overlaps, or edge
segment splits are discovered, the process notifies user-specified
callback functions defined in the visitor object, which must be a
model of the `OverlayVisitor` concept. These functions can then apply
custom logic to automatically combine, translate, or synchronize user
extended cells from the input arrangements into the resulting output
cells.

<!-- ======================================================================= -->
\section aoc_sec-geom_traits The Geometry Traits
<!-- ======================================================================= -->

<!-- ----------------------------------------------------------------------- -->
\subsection aoc_ssec-geom_traits-concepts The Geometry Traits Concept
<!-- ----------------------------------------------------------------------- -->

A model of the geometry traits must satisfy the requirements of the
`AocTraits_1` concept.  It defines the types for geometric points
(\link ArrangementOnCurve_1::Point_1 `Point_1`\endlink) and provides a
factory function producing a \link AocTraits_1::Compare_x_1 `Compare_x_1`\endlink
comparison functor. This functor must provide a strict linear ordering predicate,
returning `SMALLER`, `EQUAL`, or `LARGER` when comparing two points along the curve
direction.

In addition, the geometry traits declares two boundary-category tags:

- `AocTraits_1::Left_side_category`---tag for the left boundary.
- `AocTraits_1::Right_side_category`---tag for the right boundary.

When either tag is `Identified_side_tag`, the traits must also provide
a functor type `AocTraits_1::Is_on_identification_1` (accessed via
`is_on_identification_1_object()`) that tests whether a given
`Point_1` coincides with the identification point.  The
`Compare_x_1` functor must not be called with such a point.

<!-- ----------------------------------------------------------------------- -->
\subsection aoc_ssec-geom_traits-models Models of the Geometry Traits Concepts
<!-- ----------------------------------------------------------------------- -->

The package provides five built-in geometry traits models covering
different dimensional spaces and curve topologies:

- `Line_traits_1<Kernel>`: A minimal, scalar traits model parameterizing
  an arrangement directly using a numerical coordinate field type
  scalar along a flat number line.  Both sides are `Open_side_tag`.

- `Line_2_traits_1<Kernel>`: Supports tracking points along an
  infinite straight line embedded in 2D space.  Points are ordered by
  projecting them onto the 2D supporting line equation.
  Both sides are `Open_side_tag`.

- `Line_3_traits_1<Kernel>`: Supports tracking points along a 3D
  spatial trajectory line by projecting 3D coordinates onto its
  directional vector.  Both sides are `Open_side_tag`.

- `Line_d_traits_1<Kernel>`: Scales the 1D arrangement concept across
  arbitrary \f$d\f$-dimensional space by computing inner dot products
  across coordinate ranges via Cartesian iterators.
  Both sides are `Open_side_tag`.

- `Closed_geom_traits_2_adaptor_1<GeomTraits_2>`: Adapts a 2D geometry
  traits model (providing x-monotone curves) to the 1D arrangement
  setting.  `Point_1 = GeomTraits_2::Point_2`.
  Both sides are `Closed_side_tag`.

- `Left_closed_geom_traits_2_adaptor_1<GeomTraits_2>`: Adapts a 2D geometry
  traits model (providing x-monotone curves) to the 1D arrangement
  setting.  `Point_1 = GeomTraits_2::Point_2`.
  Left side is `Closed_side_tag` and right side is `Open_side_tag`.

- `Right_closed_geom_traits_2_adaptor_1<GeomTraits_2>`: Adapts a 2D geometry
  traits model (providing x-monotone curves) to the 1D arrangement
  setting.  `Point_1 = GeomTraits_2::Point_2`.
  Left side is `Open_side_tag` and right side is `Closed_side_tag`.

- `Open_geom_traits_2_adaptor_1<GeomTraits_2>`: Adapts a 2D geometry
  traits model (providing x-monotone curves) to the 1D arrangement
  setting.  `Point_1 = GeomTraits_2::Point_2`.
  Both sides are `Open_side_tag`.

- `Identified_geom_traits_2_adaptor_1<GeomTraits_2>`: Adapts a 2D geometry
  traits model (providing x-monotone curves) to the 1D arrangement
  setting.  `Point_1 = GeomTraits_2::Point_2`.
  Both sides are `Identified_side_tag`.

- `Circle_traits_1<Kernel>`: Supports arrangements on the unit circle
  \f$\mathbb{S}^1\f$, representing points as `Kernel::Direction_2`
  objects for exact arithmetic.  Both sides are `Identified_side_tag`;
  must be paired with `Identified_topology_traits`; see \ref
  aoc_sec-circle.

<!-- ======================================================================= -->
\section aoc_sec-topo_traits The Topology Traits
<!-- ======================================================================= -->

<!-- ----------------------------------------------------------------------- -->
\subsection aoc_ssec-topo_traits-concept The Topology Traits Concept
<!-- ----------------------------------------------------------------------- -->

The topology traits are responsible for the combinatorial storage and
navigation of the arrangement.  A model must satisfy the requirements
of the `AocTopologyTraits` concept.  It provides:

- Vertex and edge types with optional user data.
- Container and descriptor types (list-based with stable iterators, or vector-based with integer indices).
- Descriptor iterators and ranges.
- Property maps for point and user-data access.
- Core navigation (`left_edge`, `right_edge`, `left_vertex`, `right_vertex`, `has_left_vertex`, `has_right_vertex`).
- Low-level modifiers (e.g., `create_vertex`, `create_edge`, `set_*`, `erase_vertex`, `erase_edge`).

<!-- ----------------------------------------------------------------------- -->
\subsection aoc_ssec-topo_traits-base Shared Base: Topology_traits_base
<!-- ----------------------------------------------------------------------- -->

The class template `Topology_traits_base` factors out all combinatorial
infrastructure shared by the five concrete topology traits classes.
This includes the left boundary edge, which all five classes maintain.
Derived classes add only their topology-specific cached descriptors:

| Derived class                  | Extra state                                    |
|--------------------------------|------------------------------------------------|
| `Open_topology_traits`         | None                                           |
| `Closed_topology_traits`       | The left and the right boundary vertices       |
| `Left_closed_topology_traits`  | The left boundary vertex                       |
| `Right_closed_topology_traits` | The right boundary vertex                      |
| `Identified_topology_traits`   | The identification vertex                      |

`Topology_traits_base` provides:

- `Data_container<T>` and its `void` specialization (empty-base optimization) for zero-overhead optional per-cell data.
- Helper meta-types `Map_reference_traits`, `Map_const_reference_traits`,
  `Map_param_traits` to avoid `reference-to-void` compilation errors.
- `Vertex` and `Edge` node structs (with optional user data via EBO).
- Descriptor type definitions for both list mode and vector mode.
- Descriptor iterators (`List_descriptor_iterator`, `Index_descriptor_iterator`) and descriptor ranges.
- Three Boost lvalue property maps (`Vertex_point_map`, `Vertex_data_map`, `Edge_data_map`).
- Core navigation helpers (`left_edge`, `right_edge`, `left_vertex`, `right_vertex`, `has_left_vertex`,
  `has_right_vertex`, `vertex_point`).
- The left boundary edge and its accessors (`left_boundary_edge`, `set_left_boundary_edge`).
- Low-level storage primitives (`create_vertex`, `create_edge`,
  `set_left_edge`, `set_right_edge`, `set_left_vertex`,
  `set_right_vertex`, `clear_left_vertex`, `clear_right_vertex`,
  `erase_vertex`, `erase_edge`).
- The protected `patch_cross_references()` helper for list-mode copy, which also
  patches the left boundary edge.
- The protected `init_spanning_edge()` helper, which creates the single edge that
  spans the parameter space and sets it as the left boundary edge.
- The protected `clear()` helper, which removes all vertices and edges and
  recreates the spanning edge as the left boundary edge; the `clear()` functions
  of the derived classes call it and reset their own cached descriptors.
- The protected `swap()` helper, which swaps the containers and the left boundary
  edge; the `swap()` functions of the derived classes call it and swap their own
  cached descriptors.

The template parameters of `Topology_traits_base` (and all derived classes) are:

| Parameter    | Default                   | Meaning                                  |
|--------------|---------------------------|------------------------------------------|
| `Point_1_`   | (required)                | geometric point type stored at vertices  |
| `VertexData` | `void`                    | optional user data per vertex            |
| `EdgeData`   | `void`                    | optional user data per edge              |
| `UseVector`  | `false`                   | `true` = vector + index descriptors      |
| `Allocator`  | `std::allocator<char>`    | allocator for internal containers        |

Two static predicates declare the topology:

\code{.cpp}
static constexpr bool left_is_closed;   // true if Left_side_category = Closed_side_tag
static constexpr bool right_is_closed;  // true if Right_side_category = Closed_side_tag
\endcode

<!-- ----------------------------------------------------------------------- -->
\subsection aoc_ssec-topo_traits-list-vs-vector List Mode vs. Vector Mode
<!-- ----------------------------------------------------------------------- -->

The `UseVector` template parameter controls the underlying container and descriptor type:

- **List mode** (`UseVector = false`): vertices and edges are stored in
  `std::list`.  Descriptors are `std::list::iterator` objects and are
  stable across insertions.  Copying requires `patch_cross_references()`
  to redirect intra-node links.

- **Vector mode** (`UseVector = true`): vertices and edges are stored in
  `std::vector`.  Descriptors are `std::size_t` indices.  Erasing an
  element shifts subsequent indices; `erase_edge()` patches all
  intra-node cross-references automatically.
  Binary search (`BinarySearch` = `true`) is only available in vector mode.

<!-- ----------------------------------------------------------------------- -->
\subsection aoc_ssec-topo_traits-unbounded Open Topology Traits
<!-- ----------------------------------------------------------------------- -->

`Open_topology_traits` is the default topology traits for
arrangements on an open, infinite curve
(`Left_side_category = Right_side_category = Open_side_tag`).

It inherits the left boundary edge from `Topology_traits_base`.  In list
mode, it is patched after copy via `patch_cross_references()`.  In vector
mode, `erase_edge()` updates its index.

Accessor API:

| Member                             | Description                                 |
|------------------------------------|---------------------------------------------|
| `left_boundary_edge()` / `(const)` | Returns the left boundary edge descriptor.  |
| `set_left_boundary_edge(e)`        | Sets the left boundary edge descriptor.     |

<!-- ----------------------------------------------------------------------- -->
\subsection aoc_ssec-topo_traits-identified Identified Topology Traits
<!-- ----------------------------------------------------------------------- -->

`Identified_topology_traits` supports closed-loop curves
(`Left_side_category = Right_side_category = Identified_side_tag`).

\section aoc_sec-circle Arrangements on the Unit Circle \f$\mathbb{S}^1\f$
<!-- ======================================================================= -->

`Circle_traits_1<Kernel>` provides a geometry traits model for 1D
arrangements of points on the unit circle \f$\mathbb{S}^1\f$.  Points
are represented as `Kernel::Direction_2` objects.

### Parameter space and identification

The parameter space of \f$\mathbb{S}^1\f$ is \f$[0, 2\pi)\f$ with the
two endpoints identified.  Both `Left_side_category` and
`Right_side_category` are `Identified_side_tag`.  Consequently,
`Circle_traits_1` must be paired with `Identified_topology_traits`.

### Reference direction and total order

An optional reference direction \f$d_{\mathrm{ref}}\f$ (default: positive
`x`-axis \f$(1,0)\f$) defines the identification point.  The total order
on directions is the counter-clockwise (CCW) order starting strictly
after \f$d_{\mathrm{ref}}\f$:
\f$d_{\mathrm{ref}} < d_1 < d_2 < \ldots < d_n < d_{\mathrm{ref}}\f$ (one full turn).

A direction equal to \f$d_{\mathrm{ref}}\f$ is the *identification point*:
`Is_on_identification_1` returns `true` for it, and `Compare_x_1`
must not be called with it as either argument.

### Exact angular comparison

The comparison is implemented using only the kernel's orientation
predicate (no trigonometric computation):
1. Classify each direction into the *first half*
   \f$(d_{\mathrm{ref}}, d_{\mathrm{ref}}+\pi]\f$ or the *second half*
   \f$(d_{\mathrm{ref}}+\pi, d_{\mathrm{ref}}+2\pi)\f$ using the orientation of
   \f$(d_{\mathrm{ref}}, d)\f$.
2. Directions in different halves: first half \f$<\f$ second half.
3. Directions in the same half: compare by the orientation of \f$(d_1, d_2)\f$.

### Usage example

\code{.cpp}
#include <CGAL/Exact_predicates_exact_constructions_kernel.h>
#include <CGAL/Arrangement_on_curve_1/Circle_traits_1.h>
#include <CGAL/Arrangement_on_curve_1/Identified_topology_traits.h>
#include <CGAL/Arrangement_on_curve_1/Arrangement_on_curve_1.h>
#include <CGAL/Arrangement_on_curve_1/insert.h>

using K = CGAL::Exact_predicates_exact_constructions_kernel;
using Gt = CGAL::Arrangement_on_curve_1::Circle_traits_1<K>;
using Tt = CGAL::Arrangement_on_curve_1::Identified_topology_traits<Gt>;
using Arr = CGAL::Arrangement_on_curve_1::Arrangement_on_curve_1<Gt, Tt>;

int main() {
  Arr arr;
  typename Gt::Point_1 p1(1, 0), p2(0, 1), p3(-1, 0);
  CGAL::Arrangement_on_curve_1::insert(arr, p1);
  CGAL::Arrangement_on_curve_1::insert(arr, p2);
  CGAL::Arrangement_on_curve_1::insert(arr, p3);
  // arr now has 3 vertices and 3 edges on the circle.
}
\endcode


<!-- ======================================================================= -->
\section aoc_sec-extending Extending the Arrangement
<!-- ======================================================================= -->

Topological cells can be extended with custom user attributes using
template parameters for vertex and edge data inside the topology
traits.  All topology traits (including `Topology_traits_base` and its
derived classes) accept `VertexData` and `EdgeData` template
parameters.  When data types are provided, they are stored directly
inside the respective node records using an internal
`Data_container<T>` wrapper that leverages the Empty Class Optimization
(ECO) to ensure zero memory overhead when the field is `void`.

\code{.cpp}
using Tt = CGAL::Arrangement_on_curve_1::Open_topology_traits<Gt,           // GeometryTraits_1
                                                              std::string,  // VertexData
                                                              int>;         // EdgeData
\endcode

These attributes can be read or modified cleanly using standard Boost
lvalue property maps accessed via
`ArrangementOnCurve_1::vertex_data_map()` and
`ArrangementOnCurve_1::edge_data_map()`.
